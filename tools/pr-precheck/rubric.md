# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `plan-fidelity` | The plan's scope, named files, not-in-scope lines, and any deviation or deferral notes (eval: Plan context; live: `plan.md` including `## Deviations`), read side by side with the diff's changed files and behavior (eval: Candidate PR diff; live: `git diff main...HEAD`) and with the description's claims about what changed (eval: Description; live: `pr_draft.md`). | The diff stays inside the plan's stated boundary, or every mismatch is re-tied by a deviation note already in the plan and restated in the description. Fail in either direction of silent drift: the diff adds behavior, flags, options, renames, rewrites, or files the plan did not name and did not defer; or the description claims a deliverable (including "implements the plan exactly" or "docs now document this") that the diff does not contain. A limit the plan itself defers, which the description restates as deferred and the diff omits, passes. | required |
| `test-decisive` | The plan's test plan and the repro it names (eval: Plan context; live: `plan.md`), read side by side with the captured outcomes (eval: Test evidence; live: `test_evidence.md`). | Every distinct failing scenario the test plan names appears with the command or input and the observed result (output, exit code, or an explicit before and after). A control may be reported as unchanged, and a suite line may say that it passed. Fail when the failing scenario is missing and the evidence is only "tests pass", "works on my machine", a vague "it works now", or a run of a path the plan already called the control or left out of scope. A scenario the plan and the description both mark deferred is not a missing test. | required |
| `diff-reviewable` | The unified diff and the commit list (eval: Candidate PR diff and commits; live: `git diff main...HEAD`). | The planned fix is visible, and the diff does not carry debris: debug prints, commented-out code or abandoned attempts, dead or unused functions, a TODO that is not the plan's recorded deferral, or a hunk that only reindents, reprints, or reshuffles lines the plan did not ask to reformat. An explanatory comment that states why the fix is there is not debris. Whitespace that moves only because the adjacent fix line changed is part of the fix. | required |
| `standards-met` | The repo's stated PR template asks and contribution or AI policy (eval: Repo facts; live: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read side by side with the description and, for a named artifact, the diff. Also the thread, when it contains an explicit maintainer direction the template or the policy tells the author to engage. | When the repo-facts (or the live template) name concrete sections or checklist items, each one is filled with real content in the description, or the named file (changelog, whatsnew) is in the diff. A one-line answer counts, including "n/a" with a reason. A missing closes or fixes line, an empty checklist, or a required whatsnew or changelog file absent from the diff fails. Soft guide sentences that only say "add tests" or "keep it small", and a vouch process, are not a template wall. When the policy requires AI-use disclosure, the description names the tool and that a human reviewed the work; in eval mode treat the package as AI-assisted whenever that requirement exists. A policy with no disclosure requirement passes without one. | required |
| `thread-engaged` | Thread highlights (eval) or the issue thread (live), read against the description's account of the approach. | Pass when the thread has no explicit maintainer direction (a culprit file, a preferred patch, or a named open question). When it does, the description engages that direction or states why the PR diverges. A miss here is recorded and does not change the verdict. | preferred |

## Verdict rule

Accept only if every required check grades `pass`. Any required `fail` or `unclear` makes the verdict `reject`. Preferred checks never change the verdict. Treat `unclear` as `fail` for the verdict: a claim you cannot verify from the package is a claim that is not ready to submit. When the plan scope and the diff are both present, grade `plan-fidelity` pass or fail, not unclear. When a test-evidence section exists but does not show a named failing scenario, grade `test-decisive` fail, not unclear.
